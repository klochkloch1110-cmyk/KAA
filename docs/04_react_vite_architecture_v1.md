# AVL 84 - архитектура React/Vite/PWA/Supabase проекта v1

Документ фиксирует актуальное техническое направление проекта: дальнейшая разработка ведется на React/Vite с PWA-подходом, Supabase как backend-платформой и Android APK через web-to-native оболочку.

Flutter-направление считается закрытым для текущей кодовой базы. Старые упоминания Flutter в документации нужно рассматривать как исторические и заменять на React/Vite/PWA.

---

## 1. Архитектурный принцип

Для проекта нужен не тяжелый enterprise-контур, а понятная расширяемая система, которую можно довести до реальной эксплуатации маленькой компанией.

Базовый подход:

- одно основное React/Vite-приложение в `app/`;
- адаптивный web-интерфейс для руководителя: телефон, планшет, ПК;
- PWA/mobile-first интерфейс для водителя;
- Android APK для водителей через Capacitor после стабилизации PWA;
- Supabase как backend-платформа: Auth, Postgres, Storage, RLS, Edge Functions;
- простая слоистая архитектура без лишних абстракций.

Не нужно на старте делать:

- отдельное мобильное приложение на Flutter или React Native;
- тяжелый кастомный backend;
- микросервисы;
- сложную offline-first синхронизацию;
- AI-архитектуру до накопления чистых операционных данных.

## 2. Рекомендуемый стек проекта

### Клиент

- React
- TypeScript
- Vite
- Tailwind CSS
- shadcn/radix UI-компоненты по текущей базе
- PWA
- Capacitor для Android APK на этапе упаковки

### Backend-platform

- Supabase Auth
- Supabase Postgres
- Supabase Storage
- Supabase Realtime
- Supabase Edge Functions
- PostgreSQL RLS как основной механизм защиты данных

### Интеграции

- Yandex Maps: на первом этапе внешние ссылки на точки и маршрут
- Yandex Maps API: позже для поиска/выбора точек внутри интерфейса
- Yandex Vision OCR: после стабилизации рейсов и фото
- Firebase Cloud Messaging или web push: позже для уведомлений
- Sentry: мониторинг ошибок

## 3. Формат репозитория

```text
avl84_app/
  app/        React/Vite-приложение
  supabase/   SQL-миграции, Edge Functions, storage notes, seed data
  docs/       документация, ТЗ, схемы, правила
  prototypes/ исторические/визуальные прототипы
```

`app/` является основной кодовой базой приложения. Исторический Figma Make-прототип используется только как визуальный и сценарный референс, если он лежит отдельно в `prototypes/`.

## 5. Целевая организация по мере роста

Когда код начнет расти, крупные домены лучше группировать по функциональности:

```text
app/src/app/
  features/
    auth/
    dashboard/
    orders/
    trips/
    shifts/
    vehicles/
    drivers/
    documents/
    reports/
    settings/
  shared/

    hooks/

```

Правило: не переносить все сразу ради красоты. Рефакторить только те зоны, которые реально дорабатываются.

## 6. Слои ответственности

### UI / components

Содержит:

- экраны;
- формы;
- таблицы;
- модальные окна;
- локальную UI-валидацию;
- состояния loading/error/empty.

Не должен содержать:

- прямую SQL-логику;
- правила RLS;
- ручные Supabase-запросы, размазанные по компонентам.

### Store / application state

Содержит:

- текущие списки заявок, рейсов, смен, документов;
- действия приложения: создать заявку, назначить водителя, отправить рейс, закрыть смену;
- синхронизацию mock/Supabase-режима.

### Repositories

Содержат:

- работу с Supabase SDK;
- маппинг строк БД в UI-модели;
- загрузку файлов в Storage;
- вызовы Edge Functions;
- изоляцию mock-режима от реального backend.

## 7. State management

На текущем этапе используется React Context/store в `AppStore.tsx`.

Это допустимо для первого рабочего контура. Если состояние станет сложнее, можно позже рассмотреть:

- Zustand для прикладного состояния;
- TanStack Query для серверного состояния;
- React Hook Form для сложных форм.

Не нужно подключать новый state manager заранее, пока текущая модель не стала реальным ограничением.

Фактическая реализация может оставаться в виде внутреннего переключения экранов, но правила доступа обязательны:

## 9. Supabase

Клиент React/Vite обращается к Supabase напрямую для обычных CRUD-операций, но бизнес-критичные действия должны иметь серверную опору.

Критичные операции:

- генерация номера заявки;
- создание пользователя/водителя;
- генерация отчетов;
- OCR;
- push/web-уведомления;
- массовые операции с документами;
- критичные пересчеты смен и начислений.

---

## 10. Работа с заявками и справочниками

Поля текущей формы заявки считаются актуальными и не сокращаются.

Справочники должны помогать быстро создавать заявку:

- заказчики;
- организации отправителя/получателя;
- материалы;
- локации/точки погрузки и разгрузки;
- водители;
- машины.

Практичный принцип для первого релиза:

```text
Руководитель вводит новое значение в форме заявки -> система сохраняет его в справочник -> при следующих заявках предлагает автоподстановку.
```

Не нужно заставлять руководителя заранее заполнять большую админку справочников, если данные естественно появляются при создании заявок.

## 11. Яндекс.Карты

### Этап 1

Для первого рабочего релиза достаточно:

- хранить название точки;
- хранить адрес;
- хранить координаты, если они известны;
- хранить ссылку на Яндекс.Карты для точки;
- формировать ссылку на маршрут между точками A и B;
- в карточке заявки дать водителю кнопки открытия точки погрузки, точки разгрузки и маршрута во внешних Яндекс.Картах.

Это быстрее, надежнее и понятнее водителям, чем сразу встраивать сложную карту внутрь приложения.

### Этап 2

После стабилизации первого контура можно добавить:

- поиск адреса внутри формы;
- выбор точки на карте;
- сохранение координат;
- отображение мини-карты в заявке;
- более аккуратное построение маршрута.

## 12. Работа с документами и Storage

Структура хранения:

```text
documents/
  trips/{tripId}/ttn/
  trips/{tripId}/supporting/
  shifts/{shiftId}/
  expenses/{expenseId}/
  chat/{messageId}/
```

Правила:

- фото ТТН обязательно для рейсового отчета;
- имена файлов генерировать через UUID или серверно;
- оригинал сохранять всегда;
- доступ к файлам через RLS/Storage policies и signed URL;
- публичные URL для документов не использовать.

## 13. PWA и Android APK

Сначала приложение доводится как адаптивное React/Vite/PWA.

После стабилизации водительского сценария APK собирается через Capacitor:

```text
React/Vite build -> PWA/web assets -> Capacitor -> Android APK
```

Для APK заранее учитывать:

- доступ к камере/файлам для фото ТТН;
- загрузку фото в Supabase Storage;
- работу на слабом мобильном интернете;
- корректные размеры кнопок и форм для водителя;
- будущие push-уведомления.

## 14. Тестирование

Реалистичный минимум:

### Unit / logic tests

- расчеты смены;
- проверки статусов;
- мапперы данных;
- генерация/валидация отчетов.

### Component/manual tests

- форма входа;
- форма заявки;
- форма рейсового отчета;
- форма сменного отчета;
- загрузка фото;
- выгрузка отчета.

### Integration/manual tests

- авторизация через Supabase;
- водитель видит только свои данные;
- админ видит операционные данные;
- загрузка и открытие ТТН;
- закрытие смены;
- RLS smoke-checks.

## 16. Предлагаемая последовательность технического старта

1. Поднять Supabase-проект и применить миграции.
2. Подключить `.env` в `app/`.
3. Проверить вход админа и водителя.
4. Проверить RLS на тестовых пользователях.
5. Довести создание заявки со справочниками и автоподстановкой.
6. Довести назначение водителя и машины.
7. Довести водительскую карточку заявки с Яндекс-ссылками.
8. Довести рейсовый отчет с фото ТТН.
9. Довести закрытие смены.
10. Довести журнал руководителя и выгрузку.
11. После стабильного PWA-сценария подготовить Capacitor/APK.
